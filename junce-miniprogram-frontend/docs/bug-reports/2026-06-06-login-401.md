# 2026-06-06 登录模块联调 Debug 报告

## 一、Bug 概述

登录时输入错误密码，前端误弹"登录已过期，请重新登录"，而非后端返回的"用户名或密码错误"。

## 二、发现过程

在第 3 步登录页后端联调验收阶段，测试"错误密码"场景时发现。

若只测登录成功、不测错密码，此 bug 不会暴露。

## 三、现象记录（实际观测）

- **操作**：用 `shangwu` + 错误密码登录
- **前端表现**：toast 弹出"登录已过期，请重新登录"
- **Network 实际**：`POST /auth/login` 返回 `401`，Response body 为：

```json
{
  "message": "用户名或密码错误",
  "error": "Unauthorized",
  "statusCode": 401
}
```

后端返回了正确的 `message`，但前端没有使用它。

## 四、根因分析

`request.js` 的 401 分支把所有 401 一律当作"token 失效"处理（`clearLoginInfo` + 弹"登录已过期"）。

但 401 有两种不同语义：

| 类型 | 场景 | 含义 |
|---|---|---|
| 认证接口 401 | `POST /auth/login` 返回 401 | 账号密码错误 |
| 业务接口 401 | `GET /customers` 等返回 401 | token 失效 / 未登录 |

两者被一锅端，导致登录密码错被误判为 token 失效。

## 五、修复方案（最终采用）

**按 `skipAuth` 区分两类 401。**

不采用 URL 白名单、不依赖后端新增字段。

### request.js 401 分支修复前后对比

**修复前**：

```js
} else if (statusCode === 401) {
  const userStore = useUserStore()
  userStore.clearLoginInfo()
  uni.showToast({ title: '登录已过期，请重新登录', icon: 'none' })
  reject(new Error('未认证'))
}
```

**修复后**：

```js
} else if (statusCode === 401) {
  if (skipAuth) {
    uni.showToast({ title: resData.message || '登录失败', icon: 'none' })
  } else {
    const userStore = useUserStore()
    userStore.clearLoginInfo()
    uni.showToast({ title: '登录已过期，请重新登录', icon: 'none' })
  }
  reject(new Error(resData.message || '未认证'))
}
```

### 处理策略对照

| | skipAuth = true（认证类） | skipAuth = false（业务类） |
|---|---|---|
| toast | 后端返回的 `message` | "登录已过期，请重新登录" |
| 清 token | 不 | 是 |
| 清 user | 不 | 是 |
| 跳登录页 | 不（已在登录页） | 待补 |

### 为何选 skipAuth 而非其他方案

- **语义准确**：`skipAuth` 的本意就是"这个请求不需要 token"，此类请求返回 401 必然是凭证本身错误
- **零维护成本**：未来新增注册、忘记密码、短信登录等认证接口，只需同样传 `{ skipAuth: true }`，401 自动正确归类
- **不依赖 URL 白名单**：不需要维护 `/auth/*` 路径列表
- **不依赖后端**：不需要后端在响应体中新增错误码字段

## 六、修复验证（实际测试结果）

| 场景 | 操作 | 预期 | 结果 |
|---|---|---|---|
| 错误密码 | `shangwu` + 错误密码 | toast 弹"用户名或密码错误" | 通过 |
| 正确密码 | `shangwu / 123456` | 登录成功，reLaunch 跳转 customer-list，显示用户信息 | 通过 |
| 刷新持久化 | 登录后刷新浏览器 | 登录态仍在，用户信息正确显示 | 通过 |

## 八、经验教训

1. 同一 HTTP 状态码（401）可能有不同业务语义，处理时需区分上下文，不可一刀切。
2. 联调验收必须逐条走——尤其错误路径。仅测"成功场景"会漏掉此类 bug。
3. 前端拿到后端返回的 `message` 时应优先使用，不要用前端硬编码文案覆盖后端的准确信息。
4. 区分策略应选择与现有设计一致的语义锚点（如 `skipAuth`），而非引入新的判断维度。
