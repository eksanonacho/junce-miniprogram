# 君册财税 内部管理小程序 — 需求规格说明（PRD v2）

> 供 Claude Code 直接使用。本版整合客户提供的「成交客户入系统完整四步链路」及最新范围确认。
> 系统定位：财税服务公司内部管理系统（OA + 轻量 CRM + 任务流转）。
> 终端：移动端优先（uni-app，一套代码出微信小程序 + H5）。
> **本次只开发「第一期」。第二期功能仅搭壳/占位，不做真实逻辑。**

---

## 0. 范围总则（重要，先读）

### 第一期：真做
让整套客户管理流程在系统里跑起来、能用起来。包括：填单录入、自动指派、提醒确认、办件流转、办结打卡归档、任务发布与确认、角色权限、客户管理、五个看板（三个自动统计 + 两个手动录入自动整理，见下方看板范围）。

### 第二期：本次不做
涉及**自动核算、复杂周期汇总**的，本次不做：
- 佣金/工资的**自动反推计算**（即系统自动根据客户费用、交接路径算出每人该分多少。注：手动录入数字后的汇总计算，一期就做）
- 第三方成本的自动归集
- 次月初各类确认函（绩效单/工资单/收费统计等）
- 业务裂变的群协同（裂变填单可做，群协同不做）

### 看板范围（明确）
- **真做（系统自动统计业务数据）**：服务看板、老板看板、客户看板
- **半自动（手动录入 + 系统整理）**：经营看板、工资看板
  - 一期实现：提供录入页，由人手动填入数字（收入、各项成本 / 各员工底薪、佣金、提成等），看板负责**分类、汇总、加减乘除、可视化展示**。
  - 一期**不做**：系统自动从客户费用、交接路径等数据**反推**每个人该分多少佣金 / 该算多少成本。这部分自动核算放二期。
  - 边界一句话：**系统只整理人填进去的数字，不自己判断每笔钱该算给谁、该算多少。**

### 已确认事项
- 「建企业V群」=**手动**，公司自己在微信建群。**系统不自动建群、不管群**，只记录办件状态与材料归档。

## 1. 角色（RBAC）

| 角色 | 说明 |
|---|---|
| 客户主理人/商务岗 | 谈成交、首次填单提单 |
| 业务岗 | 办理具体业务、办结打卡 |
| 会计岗 | 代理户日常维护、完成任务确认 |
| 会计主管/部门主管 | 发布任务、设时效、评分；代理户合同+发票+收费协同 |
| 总务岗 | 资金/合同/发票归属、收费管控、收款确认 |
| 管理员/老板 | 全局查看、审批 |

> 注：详细权限表客户仍需补充（见第 6 节待补清单）。本期先实现基础角色隔离。

## 2. 核心业务链路（客户提供，按此实现第一期）

### 第一步：主理人填单提单
主理人谈成交后进入小程序填写：

**① 企业画像**
- 基本信息：行业、注册时间、税务类型、区域
- 企业规模：年流水、人员数
- 公司类型：一人公司 / 多股东 / 个体户

**② 服务类型**（分两大类，多选）
- 新用户：注册/地址/开户/变更/注销/代理/社保/公积金/资质（进出口备案/食品证/道路运输证/卫生证）/代理记账/财务外包/合规项目
- 代理户：同上服务项

**③ 收费标准**：一次性 / 定金+尾款

**④ 人员配置**：业务岗、会计岗、顾问岗、总务岗（指派具体人）

> 以上由主理人首次填写提单。

**权限与提醒：**
- 涉及资金、合同、发票环节，归属权限属于「总务」和「管理员」
- 提交后，相关人员收到提醒，完成「确认/阅读」动作

### 第二步：对接人办件 + 办结打卡
- 第一对接人手动建企业V群（系统不参与建群）→ 群内收材料 → 提交办件 → 办结
- 办结后回小程序完成「办结打卡」，进入下一步交接
- 需上传办结后电子材料归档
- 增加「回执接收人员」设置
- 收费管控：总务确认收费状态——已收费→直接点确认；未收费→总务向主理人发起催收动作

### 第三步：财务岗启用（仅代理户）
从业务组接收代理档案资料，办理托管入档登记：
1. 企业详细概况
2. 服务方案匹配（需发起与主理人确认）
3. 分派会计（方案审核后，发起与分派会计确认）

### 第四步：分派会计日常维护
- 主管发布月度服务计划 → 会计组全员确认
- 按时间节点（如 6/1-6/5、6/5-6/10 等），主管发起具体任务、设置时效 → 会计完成后确认
- **具体任务内容（任务1/2/3是什么）客户仍在补充（编写会计部任务中）**
- 转入户：设置会计排查问题时效反馈（可设 3 个工作日内）

**业务裂变（第一期简化版）：**
- 代理户裂变，由分派会计/主管向主理人填单（简化模板，含价格、含业务指派人）发起确认
- 相关人员确认后 → （手动邀请进群协办，系统不做群协同）→ 协办后反馈、上传办结凭证归档
- **第一期只做：裂变填单 + 确认 + 归档记录。群协同不做。**

## 3. 数据模型（核心实体）

### Customer 客户
```
id, company_name, industry, register_date, tax_type, region,
annual_revenue, staff_count, company_type(一人/多股东/个体户),
customer_category(新用户/代理户),
tier(VIP/优质/中低/0申报 —— 界定标准待客户补充),
lifecycle_stage(填单/办件中/办结/维护中/出库),
owner_id(主理人),
created_at, updated_at
```

### ServiceItem 服务项（客户选的服务，多条）
```
id, customer_id, service_type(注册/地址/开户/.../合规项目),
user_type(新用户/代理户), status(待办/办件中/办结), created_at
```

### Charge 收费
```
id, customer_id, charge_mode(一次性/定金+尾款),
amount, charge_status(已收/未收),
contract_no, invoice_no,
owner_role(资金合同发票归属: 总务/管理员),
confirmed_by(总务确认), created_at
```

### StaffAssignment 人员配置
```
id, customer_id, business_staff_id(业务岗), accountant_id(会计岗),
consultant_id(顾问岗), general_affairs_id(总务岗)
```

### WorkOrder 办件
```
id, customer_id, service_item_id, handler_id(对接人),
status(提交/办结), receipt_receiver_id(回执接收人),
archive_files(办结电子材料), completed_at
```

### Task 任务（主管→会计）
```
id, title, content, from_user_id(主管), to_user_id(会计),
deadline(时效), status(待确认/进行中/已完成),
confirmed_by_target(会计确认), created_at, completed_at
```

### TenantRegister 托管入档（第三步，代理户）
```
id, customer_id, enterprise_detail,
service_plan, plan_confirmed_by_owner(主理人确认),
assigned_accountant_id, assign_confirmed(分派会计确认)
```

### Fission 业务裂变（第一期简化）
```
id, customer_id, initiated_by(会计/主管), price,
assignee_id(业务指派人), confirmed(相关人确认),
archive_files(办结凭证), created_at
```

## 5. 关键业务规则（硬约束）
1. 涉及资金、合同、发票，操作权限仅限总务 + 管理员。
2. 填单提交后，自动给被指派人员推送提醒，对方需确认/阅读。
3. 收费未确认时，总务可向主理人发起催收动作。
4. 办结必须上传电子材料归档后，才能进入下一步交接。
5. 服务方案匹配、分派会计，均需发起对应人员确认后才生效。
6. 转入户排查问题时效默认 3 个工作日。
7. 金额相关字段用 decimal，避免浮点误差。
8. 经营看板、工资看板本期做「手动录入 + 自动整理（加减乘除、汇总、可视化）」，不做自动反推佣金/成本的逻辑（放二期）。

## 7. 技术约束
```
前端: uni-app (Vue3) → 微信小程序 + H5
后端: NestJS 或 FastAPI
数据库: PostgreSQL
权限: RBAC
部署: Docker，与 AI 初诊项目共用服务器（容器隔离），服务器以甲方名义注册
开源模板: 仅用 MIT / Apache-2.0 协议，禁用 GPL
认证: JWT
```

## 8. 数据安全
- 客户数据加密存储，传输 HTTPS
- 操作日志可追溯
- 角色越权拦截
- 文件上传归档需做类型与大小限制
