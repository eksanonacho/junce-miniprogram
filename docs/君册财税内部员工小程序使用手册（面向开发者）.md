## 一、文档定位与需求依据

本手册记录系统当前真实业务口径、技术实现、权限、状态机、测试方法和已知差距。

需求依据优先级：

1. 项目负责人最新明确指令
2. `docs/财税J师姐与XThree.docx` 中客户最新补充
3. `docs/junce_requirements_v2.md`
4. 当前已确认的业务规则
5. 当前代码
6. 历史交接和快照文档

聊天原文中的关键口径：

- 第一步：客户主理人填写企业画像、服务类型、收费标准、人员配置。
- 第二步：第一对接人建群收材料、提交办件、办结并上传材料打卡。
- 第三步：代理户进入托管，填写企业概况、确认方案、分派会计并确认。
- 第四步：主管发布计划和任务，会计确认、完成并进行日常登记。
- 业务只看业务代办，会计只看会计服务。
- 会计并非只能完成主管任务，还需要开票、咨询、账务、社保、报税、出入库和日常打卡记录。

## 三、角色与当前权限口径

| 角色 | 数据范围 | 主要写操作 |
|---|---|---|
| 商务 | 自己主理的客户 | 建客户、服务配置、人员配置、创建收费、创建办件 |
| 业务 | 关联客户和自己办理的业务办件 | 处理本人作为对接人的业务服务 |
| 会计 | 关联客户、分派托管、本人任务和会计办件 | 处理本人作为对接人的会计服务、任务确认完成、托管维护 |
| 主管 | 团队范围 | 任务发布编辑、人员配置、审批和兜底操作 |
| 总务 | 客户和收费范围 | 收费、合同、发票、催收、经营和工资录入 |
| 管理员 | 全局 | 全局管理和应急处理 |

后端是最终权限裁决方。前端必须同时隐藏不可操作入口，不允许依赖“点击后返回 403”作为正常交互。

## 四、已完成整改 1：权限入口一致性

### 4.1 问题

历史前端会向无权限角色展示操作按钮：

- 会计和业务能看到客户编辑、服务配置和创建办件入口。
- 会计能看到办件状态流转按钮，但后端拒绝。
- 主管能看到代确认/代完成任务按钮，但后端仅允许任务接收人或管理员。

### 4.2 当前规则

- 客户基本资料和服务项：客户主理人本人或管理员可修改。
- 人员配置：客户主理人、主管、管理员。
- 创建办件：客户主理人、主管、管理员。
- 任务确认和完成：任务接收人本人或管理员。
- 只读角色显示明确的只读状态，不显示无效按钮。

## 五、已完成整改 2：办件负责岗位与对接人

### 5.1 历史根因

创建办件时允许业务和会计都成为 `handlerId`，但后端 `canOperateWorkOrder` 又硬编码：

```text
roleCode === 业务 && handlerId === 当前用户
```

因此，会计成为对接人时，会计和回执业务人员都不能办理。

### 5.2 当前业务规则

- `handlerId`：实际办理人。
- `receiptReceiverId`：回执接收人，只接收交接结果。
- 普通员工能否办理取决于是否为当前 `handlerId`，不再硬编码业务角色。
- 主管和管理员保留兜底能力。
- 普通对接人的角色必须与服务负责岗位一致。
- 回执接收人必须是客户主理人或已配置的业务、会计、顾问、总务人员。

### 5.3 服务负责岗位来源

优先读取：

```text
serviceTemplate.requiredMaterials.responsibleRole
```

当前 Schema 尚无独立 `responsibleRole` 字段，因此为旧演示模板保留名称映射：

- 注册、开户、变更、资质等 → 业务
- 社保、公积金、注销、代理记账、财务外包、合规项目 → 会计
- 地址 → 商务

后续应评估将 `responsibleRole` 从 JSON 正式迁移为 ServiceTemplate 字段。

### 5.4 前端候选人

创建办件页根据服务负责角色构建 `handlerList`：

- 商务 → 客户 owner
- 业务 → staffAssignment.businessStaff
- 会计 → staffAssignment.accountant

`receiverList` 由 owner、业务、会计、总务等客户相关人员组成。

只有一个合规对接人时自动带出。没有对应岗位人员时禁止提交并提示先配置人员。

### 5.5 后端校验

涉及：

- `PermissionService.canCreateWorkOrder`
- `PermissionService.canOperateWorkOrder`
- `WorkOrdersService.validateHandlerRole`
- `WorkOrdersService.validateCustomerParticipant`
- `WorkOrdersService.resolveResponsibleRole`

对接人变更时必须重新执行岗位校验。

## 七、办件接口规则

### POST `/work-orders`

- 创建者：客户主理人本人、主管、管理员。
- 同一 ServiceItem 只能创建一条 WorkOrder。
- handler 必须与服务负责角色匹配，主管/管理员可兜底。
- receiptReceiver 必须属于客户相关人员。

### GET `/work-orders` 与 `/work-orders/:id`

- 商务：自己主理客户。
- 业务：自己是业务岗或对接人的办件。
- 会计：自己是会计岗、托管会计或对接人的办件。
- 主管、管理员：全局。

### PATCH `/work-orders/:id`

- 当前对接人、主管或管理员。
- 不能直接设置为“已打卡”。
- 变更 handler 时重新校验服务负责岗位。

### POST `/work-orders/:id/check-in`

- 当前状态必须是“办结”。
- 必须提交至少一项归档材料。
- 当前对接人、主管或管理员可操作。

## 八、当前办件状态

WorkOrder：

```text
待办 → 办件中 → 办结 → 已打卡
```

ServiceItem：

```text
待办 → 办件中 → 办结
```

Customer：

```text
填单 → 办件中 → 办结 → 维护中 → 出库
```

### 8.1 已完成的状态联动

状态联动由全局 `CustomerLifecycleService` 统一计算：

- WorkOrder `办件中` → ServiceItem `办件中`
- WorkOrder `办结` / `已打卡` → ServiceItem `办结`
- 任一办件已开始且客户尚未全部归档 → Customer `办件中`
- 所有 ServiceItem 均有关联 WorkOrder 且全部 `已打卡` → Customer `办结`
- 代理户全部归档且 TenantRegister `assignConfirmed=true` → Customer `维护中`
- Customer `出库` 是人工终态，自动同步不得重新激活

状态变更与对应 ServiceItem 更新在同一数据库事务中执行，客户生命周期也在该事务内同步。

允许的 WorkOrder 状态转换：

```text
待办 → 办件中
办件中 → 办结
办结 → 已打卡（仅 check-in 接口）
```

不允许跳级、倒退或通过 PATCH 直接设置“已打卡”。

已关联 WorkOrder 的 ServiceItem 不允许通过 ServiceItem 接口独立修改状态，防止两个状态源冲突。

涉及文件：

- `server/src/customer-lifecycle/customer-lifecycle.service.ts`
- `server/src/customer-lifecycle/customer-lifecycle.module.ts`
- `server/src/work-orders/work-orders.service.ts`
- `server/src/service-items/service-items.service.ts`
- `server/src/tenant-registers/tenant-registers.service.ts`

## 十、已完成整改 3：首次提单完整度与岗位确认

### 10.1 完整度规则

客户详情通过 `GET /customers/:id/intake-status` 获取实时状态。正式提交必须同时满足：

- 企业画像完整：`companyType`、`industry`、`registerDate`、`taxType`、`region`、`annualRevenue`、`staffCount`
- 至少存在一个 `ServiceItem`
- 客户主理人已对全部已选服务完成 `ServiceReadConfirmation`
- `StaffAssignment` 已配置业务岗、会计岗和总务岗
- 已创建 `Charge`

状态返回 `ready`、`submitted`、`missingItems`、`assignmentConfirmations`、`allAssignmentsConfirmed`、`canSubmit` 和 `canConfirm`，前端不得另写一套完整度判断。

### 10.2 正式提交与接单确认

- `POST /customers/:id/submit-intake`：仅客户主理人或管理员可调用。
- 资料不完整返回 400，并在响应中返回 `missingItems`。
- 重复正式提交返回 409。
- 提交成功写入 `Customer.intakeSubmittedAt`。
- 系统向业务岗、会计岗、总务岗及已配置的顾问岗分别创建 `customer_intake` 通知。
- `POST /customers/:id/confirm-intake-assignment`：仅该客户实际被指派人员可确认。
- 同一用户兼任多个岗位时，一次请求 upsert 本人的全部岗位确认。
- 确认记录存放在 `IntakeAssignmentConfirmation`，唯一键为 `(customerId, userId, position)`。

### 10.3 失效规则

正式提交后，只要发生以下任一修改，就将 `intakeSubmittedAt` 清空并删除该客户原岗位确认，要求主理人重新提交：

- 修改客户企业画像
- 新增或调整服务项
- 保存人员配置
- 新建或修改收费记录

这是有意设计的重新确认机制。后续若允许办件开始后修改非关键字段，应再细化为“仅关键字段变化才失效”，不能直接移除失效保护。

## 十一、已完成整改 4：会计一期手动工作台

### 11.1 一期边界

客户明确第一期“手动就行”，因此本模块不做自动绩效、自动工资或复杂会计规则计算，只集中解决会计日常登记、跨岗位同步和主管复核。

统一记录类型：

`客户入库 / 客户出库 / 开票登记 / 日常咨询 / 账务进度 / 社保明细 / 报税进度 / 年报进度 / 其他`

### 11.2 数据与接口

- 数据模型：`AccountingWorkLog`
- `POST /accounting-work-logs`：仅会计；`accountantId` 从 JWT 写入，不接受前端传。
- `GET /accounting-work-logs`：支持 `month`、`customerId`、`recordType`；按角色自动隔离数据。
- `PATCH /accounting-work-logs/:id`：会计只能修改本人尚未复核的记录；主管和管理员可纠正。
- `POST /accounting-work-logs/:id/review`：仅主管和管理员；写入复核人及复核时间。

### 11.3 数据范围

- 会计：只看本人记录；仅可为 `StaffAssignment.accountantId` 或 `TenantRegister.assignedAccountantId` 为本人的客户登记。
- 商务：只看本人主理客户的记录。
- 业务：只看本人作为业务岗关联客户的记录。
- 主管、总务、管理员：查看全部记录。
- 主管、管理员：复核。

复核后的记录状态为“已复核”，普通会计不可修改，避免周检结果被事后覆盖。
