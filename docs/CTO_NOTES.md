# CTO_NOTES.md — 技术负责人给未来接手者的提醒

> **这个文件是给谁看的**:下一任技术负责人,或任何要深度接手本项目的人/AI。
> **什么时候用**:正式接手前先通读一遍;做技术决策、改核心代码、应对客户加需求前。
> **解决什么问题**:这不是普通文档,是 CTO 视角的"哪里有雷、哪里别碰、哪里能优化"的经验交底。
> 最后更新:2026-06-09。

## 一、如果我是下一任技术负责人,我会先看什么

按这个顺序读,1 小时内能完整接手:

1. **PROJECT_CONTEXT.md** — 先搞清项目是什么、客户是谁、商务条款、一期二期边界。
2. **ROADMAP.md** — 知道整体施工顺序、当前到哪、下一步做什么、依赖关系。
3. **API_CONTRACT.md** — 看已有接口长什么样,理解后端已实现的能力。
4. **DATABASE_GUIDE.md** — 看数据模型、已有表、后续表、改库规矩。
5. **.docs**(项目内开发日志)— 看每个模块的实现细节和踩坑过程。
6. **CLAUDE.md** — 看开发铁律(每次让 AI 开发都要守的纪律)。

> 辅助:PROJECT_STATE_SNAPSHOT.md 看当前进度快照;TESTING_GUIDE.md 跑一遍回归测试确认系统是好的;SYSTEM_ARCHITECTURE.md 理解分层。

## 二、哪些地方不能乱改(动了会连锁出事)

- **金额一律 Decimal(12,2)** — 这是财税系统,改成 float 会丢精度、算错钱。已在 CLAUDE.md 固定。
- **JWT payload 里的角色信息(roleCode)** — 权限检查依赖它。改了 payload 结构,所有守卫和前端取角色的地方都会坏。
- **ownerId 从 token 获取,不接受前端传** — 这是防篡改设计。改成信任前端传,会出现"抢客户/乱归属"。
- **RoleCode 枚举(6 个角色)** — 角色编码是权限体系的根。改枚举值会让已存用户数据失效、守卫失灵。
- **已有的 Prisma migration 文件** — 别删别改。它们是数据库结构的版本历史,断了会导致迁移混乱。
- **客户生命周期枚举 LifecycleStage** — 由系统控制流转,各模块都依赖它的取值。改值要全局评估。
- **schema.prisma 里的 `moduleFormat = "cjs"`** — 删了会重现 ESM/CJS 启动报错。

## 三、哪些地方可以(也应该)后续优化

这些现在是"够用就行"的状态,等项目推进、有余力时再升级:

- **更细粒度权限** — 现在只做了基础角色隔离。等客户给权限表,补"数据级权限"(如会计只看自己客户、主管看本部门)。
- **前端 API 封装** — 统一 request 拦截器(自动带 token、统一错误处理、loading 态),前端起步时就该封装好。
- **文件上传从本地切到对象存储** — 办件归档先用本地/抽象层,量大了切到 OSS。设计时就把存储做成可替换。
- **Docker 化部署** — 现在本地直接跑,上线前补 Dockerfile + docker-compose。
- **操作日志(审计)** — 谁在什么时间改了什么,财税系统建议有。可后续加。
- **自动化数据备份** — 上线后定期 pg_dump 自动备份到异地。

## 四、当前最大技术债(真实,非泛泛)

1. **细粒度权限缺失**:所有 customers 接口目前"所有登录角色都能访问全部",没做数据级隔离。等权限表来了必须补,否则上线后会有"会计能看到全公司所有客户"的越权问题。
2. **前端尚未封装统一请求层**:前端刚起步,如果不在一开始就封装好 request(token、错误、BASE_URL),后面每个页面各写各的,改起来很痛。
3. **文件上传归档未实现且未设计存储策略**:办件模块要用,现在连本地存储抽象层都还没有,做办件前要先定存储方案。
4. **没有任何自动化测试**:目前全靠手动 curl 回归。模块多了之后,手动测会越来越重,建议适时引入接口自动化测试。
5. **联调依赖内网穿透 + 主理人开机**:前后端不同网络,目前靠 cpolar 临时联调,不稳定。后端尽早部署到云服务器能根治。

## 五、当前最大产品风险(真实)

1. **客户(纪姐)可能继续加需求** — 已多次发生(小程序、文案、企业微信都是聊着聊着加的)。每次新需求先判断属于一期还是二期,守住边界。
2. **经营/工资看板容易被误解为"全自动"** — 实际一期只做"手动录入 + 自动汇总(加减乘除)",不自动反推佣金/成本。交付/沟通时务必说清楚,否则客户期待落空。
3. **AI 九维度规则未给** — 整个 AI 初诊项目卡在这里,客户在"打磨"。AI 工期从收到规则那天才算,别让它无限期拖着尾款。
4. **第四步任务内容未明确** — 任务模块只能先做框架,内容等客户(正在编会计部任务)。
5. **客户分层标准未给** — 分层目前手动选,无法自动判断,看板按层统计会受影响。

## 六、给开发者的建议

- **继续小步快跑** — 一次只做 1-2 个模块,别贪多。
- **每个模块必须 curl 验证** — 接口做完先用 curl 测通(带 `--noproxy "*"`),再交前端、再往下做。
- **每次完成写 .docs** — 这个模块做了什么、踩了什么坑、怎么测,记下来。这是项目记忆的来源。
- **前后端通过 API_CONTRACT.md 对齐** — 后端每加接口就更新它,前端只认它。不允许前端自己编字段。
- **遵守 CLAUDE.md 铁律** — 先 plan 后 code、金额 Decimal、资金接口限总务+管理员、缺资料留 TODO 不瞎编。
- **改核心前先看第二节"不能乱改"清单** — 那些地方动之前先想清楚连锁影响。

## 七、给项目负责人(主理人)的建议

- **继续严守一期/二期边界** — 这是这个项目不亏本、能交付的生命线。任何超范围功能,援引方案书"第二期、另行计费"。
- **客户新增需求必须归档** — 每次纪姐加需求/改需求,记进 CLIENT 记录(微信确认 + 文档)。口头的不算,落到文字才有依据。
- **涉及钱的自动核算要慎重** — 佣金/工资/利润自动计算是最容易出错、最容易被追责的部分。一期坚持"手动录入+汇总",自动反推放二期、做精准再上。
- **材料没给就不要猜** — 客户没给的标准(分层、任务内容、权限),先留 TODO、做手动可配置,不要自己编规则。编错了返工 + 影响信任。
- **尽早推动后端上云** — 合同里本就含服务器。后端常驻云端能解决联调不稳、依赖开机的问题,也为上线铺路。
- **保护好开发节奏** — 你同时还要兼顾 AI 项目和可能的文案合作,别让多线并行压垮交付质量。一期交付质量 > 接更多活。
